# Component data model

Component types belong to a product and select a subset of its geometry parameters. Empty inheritance produces one shared geometry per type. A component derives canonical values from a saved configuration and stores their signature; its code is entered explicitly with the type prefix. Revisions are independent of housing revisions and support the existing model file table, hashes, profiles and immutable releases. Compatibility is an explicit pair of revisions, never inferred from historical hints. Compatible pairs must share inherited geometry. Types and component geometry are protected once used. No presets, data migration, manufacturing BOM integration or portal editing are included in this stage. Cross-product component reuse is not yet supported. Existing product and housing records are unchanged by schema creation.

The model manager lists component revisions alongside housing revisions and previews their STL files. It proposes a generic code from the type prefix and inherited values and links existing matching components. Creation and editing remain in Desk. Product-specific naming presets and historical assignment are not implemented yet.
